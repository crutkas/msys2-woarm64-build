>>> THE TWO EXECUTION POINTS (the actual residual risk) <<<

L149  cmp git-remote-http{,s}.exe               : BYTE COMPARE (cmp), NOT
        execution. Just tests if the two files are identical.
L153  usage="$( .../git-remote-http.exe 2>&1 )" : *** EXECUTES AN ARM64 PE ***
        This runs git-wrapper.exe (copied over git-remote-http.exe at L152)
        and inspects output for exit=1 + "remote-curl".
        FAILURE MODE ON x86-64: the exec fails (wrong arch) -> $?,$usage does
        NOT match "1,*remote-curl*" -> the `*)` fallback at L156 fires -> it
        just copies git-remote-https.exe over git-remote-http.exe. NON-FATAL.
        CONSEQUENCE OF RUNNING ON x86-64: you lose the git-wrapper size
        optimisation (http and https end up as two full copies instead of one
        tiny wrapper) but the artefact is STILL COMPLETE AND CORRECT.
L169  uname="$( .../ash.exe -c uname 2>&1 )"     : *** EXECUTES AN ARM64 PE ***
        Runs git-wrapper.exe (copied to ash.exe at L168) as `ash -c uname`,
        checks exit=0 + "BusyBox".
        FAILURE MODE ON x86-64: exec fails -> not "0,*BusyBox*" -> `*)` at
        L172 REMOVES ash.exe. NON-FATAL to the archive, BUT the resulting zip
        would then LACK ash.exe — and ash.exe is the busybox-shell entry point
        the --busybox MinGit is built around. So on x86-64 this step would
        SILENTLY DROP the shell wrapper.
L181  7z a -mx9 "$TARGET" $LIST root/*          : archiver. No ARM64 exec.

--- CONCLUSION (DERIVED from the above, MEASURED reads) ---

TWO steps execute ARM64 binaries: L153 and L169. Both are git-wrapper.exe
"is-this-wrapper-usable?" probes.
  * L153 degrades gracefully to a correct-but-larger artefact if it cannot
    execute -> a real ARM64 host is PREFERRED but not REQUIRED for correctness.
  * L169 does NOT degrade gracefully for the --busybox path: on a non-ARM64
    host it removes ash.exe, producing a MinGit without its shell entry point.
    -> A REAL ARM64 HOST IS REQUIRED for the final --busybox assembly to keep
    ash.exe. This is a SCHEDULING FACT: the real assembly must run on THIS
    Windows ARM64 machine, not under x86-64 WSL.

--- git-wrapper.exe PROVENANCE (MEASURED) ---
Searched: build-extra (grep git-wrapper) -> only release.sh, installer/
install.iss, git-extra/git-extra.install.in.
  * git-extra/PKGBUILD package() (lines 150-190): installs create-shortcut,

    git-credential-helper-selector, git-askpass, git-update, etc. It does NOT

    "Drop git-wrapper in place of builtins to save space;
     git_wrapper=@@MINGW_PREFIX@@/share/git/git-wrapper.exe".
  * The upstream MSYS2 clangarm64 git-2.55.0.5 reference package does NOT ship
    share/git/git-wrapper.exe (measured: it has only share/git/completion/*).
CONCLUSION: git-wrapper.exe is shipped by GIT-FOR-WINDOWS OWN git build (the
G4W git package), NOT by the MSYS2 git package and NOT by git-extra. It lands
at <arch>/share/git/git-wrapper.exe. It is a Git-for-Windows patch/artefact.
