THE SORT: direct-drive (gcc/ar, no shell) vs needs-configure — MEASURED per package.

METHOD: fetched each source, inspected build system + whether sources are self-contained or depend on
generated/gnulib files. Where cheap, ATTEMPTED a direct-drive build and recorded the exact failure.

=== DIRECT-DRIVE — PROVEN (built natively, RUN-verified) ===
 1. wineditline 2.208  [DONE] cmake nominally, but 3 self-contained .c -> drove gcc/ar directly. RUN ok.
 2. brotli 1.2.0       [DONE] cmake nominally, 35 self-contained .c, version.h in-tree -> drove directly.
                       Static + shared (dllexport macros) both RUN=55. (See auto-import defect note.)

=== NEEDS-CONFIGURE — MEASURED BLOCKER (gnulib / generated sources) ===
 3. libtasn1 4.21.0    autotools+gnulib. ATTEMPTED direct-drive, FAILED (measured):
      - lib/*.c #include "c-ctype.h", "intprops.h" — GNULIB headers NOT in tarball lib/; they are copied in
        by the gnulib bootstrap that ./configure/automake drives. 
      - uses gnulib replacements strverscmp(), MAX() macro — supplied by gnulib, absent without it.
      - ASN1.c is generated from ASN1.y (bison grammar) — needs bison + the generator step.
      => CANNOT direct-drive. Needs ./configure (=> needs sh) OR a full gnulib import + bison run.
 4. libunistring 1.4.2 autotools+gnulib (same family; huge gnulib footprint). DERIVED same blocker.
 5. libffi 3.8.0       autotools; has target asm (aarch64) selected by configure + ffi.h/fficonfig.h
                       generated by configure. DERIVED needs-configure.
 6. libidn2 2.3.x      autotools+gnulib. DERIVED same blocker as libtasn1.
 7. libssh2 1.11.1     autotools (or cmake). Generates libssh2_config.h; cmake path could be ninja-driven.
 8. c-ares 1.34.8      cmake or autotools; generates ares_config.h. cmake+ninja candidate.
 9. libpsl 0.21.5      meson (generates config.h + suffix data). meson+ninja candidate.
10. p11-kit 0.26.5     meson (large, needs libtasn1+libffi first). meson+ninja candidate.

=== CONCLUSION (measured + derived, labelled) ===
* Direct-drive works ONLY for packages whose sources are self-contained (no gnulib, no generated .c). That is
  wineditline + brotli — both DONE.
* The remaining 8 all require config.h/generated-header/gnulib-file generation. That generation is driven by
  ./configure (autotools) or meson — BOTH REQUIRE A SHELL. Meson/cmake packages can then build with ninja
  (which runs standalone here), but the CONFIGURE step still needs sh.
* THEREFORE the remaining 8 are GATED ON THE SAME SHELL that busybox-w32 (session 1e7a7fd3) is producing.
  This is not a per-package failure of our compiler — the COMPILER builds the objects fine (libtasn1's 9 .c
  would compile once gnulib headers exist). It is the BUILD-DRIVER gate, exactly as measured earlier.
* Hand-writing config.h is viable ONLY for tiny non-gnulib packages; for gnulib-based ones it means importing
  the entire gnulib subset by hand = fragile and correctness-risky (wrong HAVE_/SIZEOF => silent bugs). NOT
  recommended as the honest path.

RECOMMENDATION: ship wineditline + brotli now (done). Hold the other 8 for the busybox-sh unblock from
1e7a7fd3, then build them with configure/meson + our native GCC as CC. That is the honest, correct route and
it keeps the compiler-attribution clean (our GCC compiles every object; only the orchestration is borrowed sh).
